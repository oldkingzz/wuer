# 导航 / 寻墙 / Mission 当前存在的“不足”

> 本文件用来记录目前整体逻辑不够顺、未来需要改进的点，方便之后统一重构。

---

## 1. 模式与行为预期不一致

### 1.1 用户期望的高层流程

理想中的自动流程大致是：

1. 从 **手动模式切换到自动** 时，系统自动开始 **寻墙（wall following）**，小车从固定起点出发，沿着场地边缘走，手机上能看到自己沿线移动；
2. 在自动过程中，如果用户在网页上选择任意一个 **目标点 / 预设 Mission**：
   - 小车执行一整套 Mission 状态机（先导航到 pre-point，再对齐、顶按钮、后退等）；
3. **Mission 完成后，如果没有新的任务命令**：
   - 小车应当 **自动回到寻墙行为**，继续绕场地走；
4. 寻墙本身不依赖 Vive，全靠 ToF + IMU + 里程计即可。

### 1.2 当前实现的真实逻辑

根据现有代码：

- `MODE = { MANUAL, WALL_FOLLOW, NAVIGATION }` 只是一个 **互斥状态标记**：
  - `switchMode()` 在切换时会调用：
    - 从 WALL_FOLLOW 退出：`/stopWallFollow`
    - 从 NAVIGATION 退出：`/stopNav`
    - 从 MANUAL 退出：`/stopChassis`
  - 但 **不会自动启动寻墙或导航**，真正的启动由各自按钮 / 操作触发：
    - 点“START WALL FOLLOWING” → `/startWallFollow`
    - 点击地图设目标 → `/setNavGoal`
    - 未来 Mission 预设按钮 → `/startNavPreset?id=...`

- Wall-follow（寻墙）逻辑：
  - 完全 **不使用 Vive**，只用 ToF + IMU + 编码器；
  - `WF_STATE_INIT_POS` 假设小车被放在 **右上角、前方和右侧都有墙** 的固定起点；
  - 根据前/右 ToF 推出在 60×144 英寸地图中的初始 `(x, y, heading)`，然后从最近的路径点 `g_path[i]` 开始沿一圈预设轨迹走；
  - 走完一圈后状态变为 `WF_STATE_STOPPED`，小车停止，不会自动循环下一圈。

- Mission（预设目标点状态机）：
  - `/startNavPreset?id=X` → 调 `nav_mission_start(goal_id)`：
    1. 通过 `vive_nav_set_target_goal(goal_id)` 设置 A* 目标（需要 Vive 位姿）；
    2. `vive_nav_start()` 开始低层导航；
    3. Mission 状态机依次执行 `GOTO_PRE_POINT → ALIGN_TOF → FORWARD_IMPACT → RETURN`；
  - Mission 结束时状态为 `DONE` 或 `ERROR`，会停车，但 **不会自动调用 `wall_following_start()`**；
  - 想重新寻墙，必须用户 **再次手动点击“START WALL FOLLOWING”**。

**结论：** 目前实现的行为和用户期望的“自动 → 寻墙 → Mission → 自动回寻墙”并不一致，这一块将来需要设计一个统一的高层状态机（自动模式下的主循环）。

## 2. 地图与模式的脱节

### 2.1 当前地图显示用的位姿

- 导航地图使用 `/getNavStatus` 返回的：
  - `robot_x`, `robot_y`, `path[]` 等信息；
  - 这些都是 **Vive 导航系统** 内部的地图坐标（1 英寸 / 像素 + A* 路径）。

- Wall-follow 的位姿：
  - 在 `wall_following.cpp` 内部用 IMU + 编码器 + ToF 维护，
  - 没有暴露到 `/getNavStatus`，也没有在地图上画出来。

因此：

- **地图上画出来的轨迹是 Vive 导航 / Mission 用的那一套**；
- 当小车在跑寻墙（Wall-follow）时，
  - 地图上看不到它“沿着边线移动”的真实路径；
  - 只能通过 Wall-follow 状态 + ToF 数值大致推断位置。

这会让整体体验感觉“逻辑不连贯”：

- 自动模式下有两套独立的“世界观”：
  - 一套是 Wall-follow 的 60×144 英寸坐标 + 预设巡线路径；
  - 另一套是 Vive 导航的像素地图 + A* 路径；
- 但网页上只有一张地图，当前只展示 Vive 那一套。

未来可以考虑：

1. 统一 / 映射两套坐标系，在同一张地图上绘制：
   - 寻墙路径 + 当前寻墙位置；
   - Mission / 导航路径 + 当前 Vive 位置；
2. 或者在前端通过模式区分清楚“当前显示的是哪个子系统的位姿”。

## 3. Web UI 与真实地图 / 行为不匹配

### 3.1 现有网页地图的问题

- `web.h` 中当前的 Navigation Map：
  - 只是一个 **示意图**，结构和真实场地不一致；
  - 用户可以点击任意点发送 `/setNavGoal?x=..&y=..`，但这与真实比赛地图的逻辑、预设目标点并不完全一致；
  - 在手机上使用时，布局也不够友好。

### 3.2 期望的 Web 行为

用户偏好：

1. Joystick 和 Real-time Sensor Data **保持不变**；
2. Wall Following 和 Navigation Map **合并为一个统一的“自动模块”**：
   - 不再是两个割裂的卡片；
   - 以一张尽可能接近真实场地的地图为核心；
3. 不再保留“点地图设导航目标”的功能；
4. 地图主要承担：
   - 显示小车在场地中的大致位置；
   - 展示当前路径（寻墙路径 / Mission 路径）；
5. 页面整体偏向 **手机友好布局**。

这意味着：

- 现有 `web.h` 中 Navigation Map 相关的 HTML/JS 需要重构；
- Mission 的控制（`/startNavPreset`, `/getMissionStatus`）需要在这个统一模块里加入 UI；
- 将来若要在 Mission 完成后自动回到寻墙，也需要前端或后端在同一套 UI / 状态机里体现出来。

---

## 4. 明确的改进方向（备忘）

1. **高层自动模式状态机：**
   - 设计一个统一的“自动模式”主循环：
     - Auto 模式下默认先启动寻墙；
     - 收到 Mission 命令时，挂起寻墙 → 执行 Mission；
     - Mission `DONE` 后，自动恢复寻墙；
   - 注意与手动模式、纯导航（只去某一点不做撞击）之间的关系。

2. **坐标系与地图展示统一：**
   - 明确 Wall-follow 的 60×144 英寸坐标与 Vive 像素地图的关系；
   - 考虑在 `/getNavStatus` 或新的接口中，加入 wall-follow 位姿；
   - 在前端地图上用不同颜色 / 图层展示不同子系统的轨迹。

3. **Web UI 重构（Step5）：**
   - 保留 Joystick + 实时传感器区不变；
   - 合并 Wall Following + Navigation Map 为一个“Autonomous / Mission”模块；
   - 去除点击地图设目标的功能；
   - 增加 Mission 预设按钮与状态显示（调用 `/startNavPreset` + `/getMissionStatus`）；
   - 地图更新为更接近真实场地的布局，并体现出起点固定这一事实。

4. **自动回到寻墙（未来必做）：**
   - 已确认 **“Mission 完成后自动恢复寻墙” 是未来希望加入的功能**；
   - 在重构时，应预留好：
     - 后端：Mission 状态变化时可以触发 `wall_following_start()` 或发事件；
     - 前端：监听 `/getMissionStatus`，检测 `mission_state == DONE` 时自动调用 `/startWallFollow`（可配置开关）。

> 以上内容只是记录当前“不足”和重构方向，不代表已经实现。具体设计与参数需要在实际调试和比赛规则下进一步细化。
